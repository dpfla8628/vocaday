# 일기 댓글, 검증된 패턴과 이중 잠금으로 설계하라

국내외 댓글 UI는 이미 하나의 구조로 수렴해 있다. 두 사람이 주고받는 모바일 일기 댓글은 그 공통 구조를 그대로 가져다 쓰면 된다. 실제 배포 CSS를 열어 보면 당근 동네생활, 네이버 카페, 브런치는 모두 **32–36px 원형 아바타, 8px 간격, 그만큼 들여쓴 40–44px 텍스트 열, 15–16px 본문과 22–24px 행간**을 쓴다. 대댓글은 페이스북·인스타그램과 마찬가지로 **한 단계만** 허용하고, 부모 댓글 텍스트가 시작하는 위치(40–44px)에 맞춰 들여쓴다. 국내 플랫폼은 수정·삭제를 오른쪽 위 ⋯ 메뉴 뒤에 두고, 지워진 부모 댓글은 회색 안내 문구로 자리를 남겨 답글의 맥락을 지킨다. '수정됨' 표시는 거의 쓰지 않는다. 중복 제출 방지 모범 사례는 네 단계로 겹친다. 탭하는 순간 버튼 문구를 "등록 중…"으로 바꾸고, 스피너는 약 400ms가 지나야 띄우고, 잠금은 해당 댓글의 컨트롤로만 좁히고, 최종 방어는 클라이언트가 만든 멱등 키를 받은 서버가 맡는다. 접근성 쪽에서는 네이티브 `disabled`를 피하는 흐름이 뚜렷하다. `disabled`는 포커스를 날려 버리므로, 버튼은 포커스를 받을 수 있게 두고 `aria-disabled="true"`와 JS 가드로 막는다. `aria-busy`는 버튼이 아니라 갱신 중인 댓글 목록에 붙이고, 상태 변화는 페이지 로드 때부터 있던 `role="status"` 영역으로 알린다. 아래 수치는 당근·네이버 카페·브런치의 2026년 10월 배포 코드와 Ant Design·Primer 소스에서 직접 확인한 값이다. 인스타그램·유튜브·디스코드는 픽셀 사양을 공개하지 않고, 네이버 블로그·다음 카페·에브리타임은 로그인이나 접근 제한 때문에 측정하지 못했다.

## 국내 플랫폼의 댓글은 몇 px 차이로 같은 구조다

국내 세 플랫폼의 실측값은 서로 몇 px씩만 다르다. 당근 동네생활 웹 댓글은 **36×36px 원형 아바타** 옆에 8px 간격을 둔다. 닉네임은 16px/24px에 굵기 600, "동네명 · 6일 전" 메타는 14px/20px에 회색 #868B94, 본문은 16px/24px(1.5)이다. 헤더·본문·액션 행은 flex `gap: 8px`로 묶는다 ([당근 동네생활](https://www.daangn.com/kr/community/%EC%83%A4%EC%9B%8C%EA%B8%B0%EA%B1%B0%EC%B9%98%EB%8C%80-%ED%9C%B4%EC%A7%80%EA%B1%B8%EC%9D%B4-%EC%88%98%EA%B1%B4%EA%B1%B8%EC%9D%B4-h9v1co6o28y6/)). 네이버 카페 모바일 웹은 **34px 아바타**, 14px·굵기 600 닉네임, 자간 -0.3px의 16px/22px 본문을 쓴다. 본문은 `padding-left: 42px`(34+8)로 들여서 닉네임과 줄을 맞춘다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css)). 브런치는 32px 아바타, 13px 이름, 12px 시간, **15px/24px(1.6)** 본문으로 셋 중 가장 여유 있는 편집형 분위기를 낸다 ([브런치 댓글 CSS](https://t1.kakaocdn.net/brunch/home_front/prod/20260928145833/_astro/comment.CouC7HU1.css)). 디자인 시스템 중 소스 코드로 수치를 확인할 수 있었던 Ant Design 4.x Comment도 같은 구조다. 32px 아바타, 12px 간격, 14px 이름과 본문, 12px 메타, 댓글마다 위아래 16px 패딩을 쓴다 ([antd comment less](https://raw.githubusercontent.com/ant-design/ant-design/4.x-stable/components/comment/style/index.less); [antd default.less](https://raw.githubusercontent.com/ant-design/ant-design/4.x-stable/components/style/themes/default.less)).

| 항목 | 당근 동네생활(웹) | 네이버 카페(모바일 웹) | 브런치(PC 웹) | Ant Design 4.x |
|---|---|---|---|---|
| 아바타 | 36px | 34px | 32px | 32px |
| 아바타–텍스트 간격 | 8px | 8px | 8px | 12px |
| 이름 | 16/24px, 600 | 14px, 600 | 13/22px | 14px |
| 시간·메타 | 14/20px, #868B94, 이름 아래 | 14px, #8f9194, **본문 아래** | 12/20px, #959595 | 12/18px, #ccc |
| 본문 | 16/24px, `keep-all` | 16/22px, -0.3px, `break-all` | 15/24px | 14px, 1.5715 |
| 댓글 사이 구분 | `gap: 16px`, 선 없음 | 위아래 14px + 1px #f5f6f7 선 | 위아래 마진 36px + 1px #eee 선 | 위아래 패딩 16px |

진짜 차이는 수치가 아니라 댓글을 서로 구분하는 방식에 있다. 당근은 최상위 댓글 `<ul>`을 `gap: 16px` flex로 두고 모든 `<li>`의 테두리·패딩·배경을 0으로 만든다. **선도 카드도 없이 여백만으로 구분한다** ([당근 동네생활](https://www.daangn.com/kr/community/%EC%83%A4%EC%9B%8C%EA%B8%B0%EA%B1%B0%EC%B9%98%EB%8C%80-%ED%9C%B4%EC%A7%80%EA%B1%B8%EC%9D%B4-%EC%88%98%EA%B1%B4%EA%B1%B8%EC%9D%B4-h9v1co6o28y6/)). 네이버 카페는 댓글마다 1px #f5f6f7 가는 선을 긋고, 댓글 영역이 끝나면 10px 두께의 구분선을 둔다. 브런치는 댓글 하나에 위아래 36px 마진과 1px #eee 선을 준다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css); [브런치 댓글 CSS](https://t1.kakaocdn.net/brunch/home_front/prod/20260928145833/_astro/comment.CouC7HU1.css)). 댓글이 몇 개뿐인 두 사람의 일기라면 당근식 여백 구분이 가장 가볍다. 네이버식 가는 선은 길고 촘촘한 목록에서나 제값을 한다. 오히려 눈여겨볼 것은 네이버 카페가 **내 댓글(`li.mine`)에만 #f5f6f7 배경을 깔아** 구분하는 방식이다. 참여자가 둘뿐인 대화에서는 같은 아바타를 반복하는 것보다 배경색 하나가 "누가 쓴 글인지"를 더 빨리 알려 준다.

시간 표시는 형식과 위치 모두 플랫폼마다 다르다. 네이버 카페 JS 번들을 보면 1분 미만은 "방금 전", 이후 "N분 전", "N시간 전", 7일 미만은 "N일 전"으로 쓴다. 그 뒤로는 같은 해면 "MM.DD.", 다른 해면 "YYYY.MM.DD."처럼 끝에 마침표를 붙인다. 다만 임계값 상수가 압축돼 있어 분·시간·일 경계는 출력 문자열을 보고 추정했다 ([네이버 카페 모바일 JS](https://ca-fe.pstatic.net/web-mobile/js/app.2dd3b3f070bc.js)). 위치도 다르다. 네이버 카페는 날짜를 헤더가 아닌 **본문 아래 푸터**에 14px 회색으로 두고 그 옆에 "답글쓰기" 텍스트 버튼을 붙인다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css)). 당근은 이름 바로 아래 메타 줄에 `<time>` 요소로 넣는다. Atlassian Comment는 작성자·시간·수정 표시를 한 헤더 줄에 묶는다 ([Atlassian Comment](https://atlassian.design/components/comment/examples)). 브런치는 "Jan 8. 2024" 같은 영문 날짜를 쓴다 ([브런치](https://brunch.co.kr/@brunch/1)). 인스타그램의 "2h"나 유튜브의 "2시간 전" 형식은 출처로 확인하지 못했다. 일기 앱에는 네이버 카페식 상대 시간을 `<time datetime="...">` 요소에 담아 이름 옆 메타 줄에 두는 방식이 가장 무난하다.

타이포그래피와 대비에는 공식 기준이 있다. KRDS(대한민국 정부 디자인 시스템)는 **본문 최소 16px, 행간 150% 이상**을 요구한다 ([KRDS 타이포그래피](https://www.krds.go.kr/html/site/style/style_03.html)). 당근의 SEED 디자인 시스템은 t5 토큰을 16/22로 정의했지만, 실제 동네생활 댓글은 16/24를 쓴다 ([SEED Typography](https://seed-design.io/docs/foundation/typography)). 한국어 줄바꿈은 플랫폼마다 갈린다. 당근은 `word-break: keep-all`, 네이버 카페는 `break-all`을 쓰고, 브런치는 keep-all 폴리필을 따로 싣는다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css); [브런치](https://brunch.co.kr/@brunch/1)). `keep-all`은 한글을 음절이 아닌 어절 단위로 줄바꿈한다 ([MDN word-break](https://developer.mozilla.org/docs/Web/CSS/Reference/Properties/word-break)). 영어 일기 본문에는 영향이 작지만 한영 혼용 문장과 한국어 UI에는 도움이 되고 부작용이 없다. 긴 URL이 넘치지 않도록 `overflow-wrap: anywhere`를 함께 건다. 회색 메타 텍스트는 대부분 대비 기준을 통과하지 못한다. WCAG 상대 휘도 공식으로 흰 배경 대비를 직접 계산하면 당근 #868B94는 약 3.4:1, 네이버 카페 #8f9194는 약 3.2:1, 브런치 #959595는 약 3.0:1, Ant Design #ccc는 약 1.6:1이다. 모두 KRDS가 일반 텍스트 AA 기준으로 명시한 **4.5:1**에 못 미친다 ([KRDS 타이포그래피](https://www.krds.go.kr/html/site/style/style_03.html)). 12–14px 메타에는 #6B7280(약 4.8:1)이나 그보다 진한 색을 쓴다. Atlassian은 각 댓글의 작성자 줄을 일관된 제목 수준(기본 h3)으로 마크업하라고 권한다. 그러면 스크린리더 사용자가 댓글 단위로 건너뛸 수 있다 ([Atlassian Comment](https://atlassian.design/components/comment/examples)).

## 대댓글은 어디서나 한 단계만, 들여쓰기는 아바타+간격만큼

국내 세 플랫폼은 모두 대댓글을 한 단계만 허용하고, 연결선이나 'ㄴ' 기호를 쓰지 않는다. 당근은 답글 컨테이너에 `padding: 12px 0 0 44px`를 준다. 답글끼리는 **12px 간격**으로 최상위 댓글 사이 16px보다 촘촘하고, 답글 아바타는 36px 그대로이며, 왼쪽 선은 없다 ([당근 동네생활](https://www.daangn.com/kr/community/%EC%83%A4%EC%9B%8C%EA%B8%B0%EA%B1%B0%EC%B9%98%EB%8C%80-%ED%9C%B4%EC%A7%80%EA%B1%B8%EC%9D%B4-%EC%88%98%EA%B1%B4%EA%B1%B8%EC%9D%B4-h9v1co6o28y6/)). 네이버 카페는 답글(`li.reply`)을 42px 들이고 테두리를 없애 부모에 붙여 보이게 한다. **답글 아바타는 34px에서 28px로 줄이고**, 답글 묶음이 끝난 다음 최상위 댓글 위에만 1px 선을 그어 묶음을 닫는다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css)). 브런치는 `padding-left: 40px`(32+8)를 쓴다 ([브런치 댓글 CSS](https://t1.kakaocdn.net/brunch/home_front/prod/20260928145833/_astro/comment.CouC7HU1.css)). Ant Design의 `margin-left: 44px`(32+12)도 같은 계산이다 ([antd comment less](https://raw.githubusercontent.com/ant-design/ant-design/4.x-stable/components/comment/style/index.less)). 넷 다 들여쓰기 폭이 정확히 부모의 텍스트 시작점과 같다. 그래서 답글 아바타가 부모 본문 첫 글자 바로 아래에 놓이고, 위계는 들여쓰기와 묶음 안의 구분선 없음만으로 전달된다.

해외 SNS도 결론은 같다. 페이스북은 한 단계 중첩만 지원한다. 그 때문에 답하는 대상 댓글이 화면 밖에 있으면 맥락을 잃는다는 외부 관찰이 있다 ([GreaterWrong 댓글](https://www.greaterwrong.com/posts/tFwNi24kXeZ2BzvZz/shortform-beta-launch/comment/QZEFhkQRKj6gWncdg)). 인스타그램은 한 단계로 평평하던 댓글이 대화를 따라가기 어렵다는 이유로 답글 스레드를 도입했다. 답글은 부모 아래에 들여쓰기로 표시되며 ([Digital Trends](https://www.digitaltrends.com/?p=1228129); [WERSM](https://wersm.com/?p=49309)), 2026년 7월 기준으로 **최상위 댓글과 답글의 두 층**이다 ([SociaVault](https://sociavault.com/blog/instagram-comment-replies-api)). 유튜브는 2025년 Premium 사용자에게 "Reddit에서 영감을 받은" 스레드 UI를 시험한 뒤 일반 사용자에게도 확대했다 ([AlternativeTo](https://alternativeto.net/news/2025/7/youtube-tests-threaded-comment-ui-and-nested-replies-for-premium-users); [Android Authority](https://www.androidauthority.com/youtube-redesign-android-3609898/)). 하지만 생긴 것은 프로필 사진과 답글을 잇는 선뿐이고, 답글을 열면 그 아래는 스레드로 나뉘지 않아 "대체로 겉모습만 바뀌었다"는 평가를 받았다 ([Yahoo Tech/Android Police](https://tech.yahoo.com/general/articles/youtubes-redesign-threading-thin-ice-182025815.html)). 깊이 중첩하는 Reddit류 앱에서는 탭으로 스레드를 접는 동작이 투표·링크 탭과 겹쳐 오작동한다는 불만이 꾸준하다 ([Lemmy 토론](https://lemmy.mariusdavid.fr/post/94118)). 위키미디어 한국어 위시리스트 문서도 모바일에서 들여쓴 스레드는 한 줄에 한 글자까지 짓눌린다고 지적한다 ([Wikimedia W239](https://meta.wikimedia.org/wiki/Community_Wishlist/W239/ko)). 반대 방향으로 간 사례가 카카오톡 오픈채팅이다. 카카오톡은 2025년 9월 오픈채팅 커뮤니티에 이어 2026년 1월 28일 v26.1.0에서 일반 오픈채팅의 '답장'을 메시지 아래 붙는 **댓글 스레드**로 바꿨다 ([디자인 컴퍼스](https://designcompass.org/2026/01/29/%EC%8A%AC%EB%9E%99%EC%9D%84-%EB%8B%AE%EC%9D%80-%EC%B9%B4%EC%B9%B4%EC%98%A4%ED%86%A1-%EC%98%A4%ED%94%88%EC%B1%84%ED%8C%85-%EB%8C%93%EA%B8%80/)). 2026년 5월 15일 v26.4.0에서는 댓글의 댓글까지 추가했다 ([카카오 보도자료](https://www.kakaocorp.com/page/detail/12037)). 이는 수백 명이 동시에 떠드는 채팅방에서 대화를 갈라내기 위한 장치다. 두 사람의 일기 스레드에 깊은 중첩이 필요하다는 근거는 아니다.

답글 대상은 이름을 본문 앞에 붙여서 표시한다. 네이버 카페는 `.reply_to`에 굵기 600의 **파란색 #0076ff 이름**을 답글 본문 앞에 붙이고, 브런치는 #eee 배경의 회색 멘션 칩을 쓴다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css); [브런치 댓글 CSS](https://t1.kakaocdn.net/brunch/home_front/prod/20260928145833/_astro/comment.CouC7HU1.css)). Slack 모바일은 메시지를 탭해 "Reply in Thread"를 고르거나 "Add a reply" 입력란에 바로 써서 스레드에 답한다. 별도 답글 상자 없이 스레드 입력창 하나를 쓰는 구조다 ([Slack 도움말](https://slack.com/help/articles/115000769927-Use-threads-to-organize-discussions-)). 답글 접기의 최신 데이터는 없다. 2021년 기준으로 네이버 카페는 답글을 모두 펼쳐 보였고, 오늘의집은 답글이 1개를 넘으면, 당근은 2개 이상이면 '더보기'로 접었다. 지금은 바뀌었을 수 있다 ([요즘IT, 2021](https://yozm.wishket.com/magazine/detail/670/)). 브런치는 목록 위쪽의 "이전 댓글 더보기" 바로 오래된 댓글을 나눠 불러온다 ([브런치 댓글 CSS](https://t1.kakaocdn.net/brunch/home_front/prod/20260928145833/_astro/comment.CouC7HU1.css)).

일기 앱의 결론은 분명하다. 깊이는 1단계로 고정하고, 답글에 다시 답할 때도 1단계에 두되 네이버 카페처럼 굵은 색 "@이름"을 앞에 붙인다. 들여쓰기는 부모 아바타+간격(44px)으로 맞춘다. 답글 아바타는 28px(네이버 카페)이나 24px(Ant Design `@avatar-size-sm`)로 줄여, 360px 폭 화면에서 본문 폭을 아끼면서 위계를 보인다. 연결선은 필요 없다. 쓰고 싶다면 Primer처럼 2px 굵기의 옅은 테두리색 세로선 하나면 된다 ([Primer Timeline CSS](https://raw.githubusercontent.com/primer/react/main/packages/react/src/Timeline/Timeline.module.css)). 참여자가 둘이라 답글 수가 적으니 기본은 모두 펼친다. 3개를 넘을 때만 "답글 N개 더보기" 텍스트 버튼을 터치 영역 높이를 충분히 확보해 두고, 아무 곳이나 탭하면 접히는 Reddit 방식은 피한다. 위 근거를 합친 시작값은 다음과 같다. 이름 15px처럼 출처 사이 중간값을 고른 항목은 판단에 따른 값이다.

```css
:root{
  --avatar:36px; --avatar-reply:28px; --gap-avatar:8px;
  --indent:44px;              /* 부모 아바타 36 + 간격 8 = 당근 */
  --gap-comment:16px; --gap-reply:12px;
  --fs-name:15px; --fs-meta:13px; --fs-body:16px; --lh-body:1.5;
  --c-meta:#6B7280;           /* 흰 배경 대비 약 4.8:1 */
  --touch:44px;
}
.comment-list{display:flex;flex-direction:column;gap:var(--gap-comment)}
.comment{display:flex;gap:var(--gap-avatar)}
.comment__avatar{width:var(--avatar);height:var(--avatar);border-radius:50%;flex-shrink:0}
.comment__body{flex:1 1 auto;min-width:0}
.comment__text{font-size:var(--fs-body);line-height:var(--lh-body);
  white-space:pre-wrap;word-break:keep-all;overflow-wrap:anywhere}
.comment.is-mine{background:#f5f6f7}   /* 네이버 카페 li.mine 방식 */
.replies{padding:12px 0 0 var(--indent);display:flex;flex-direction:column;gap:var(--gap-reply)}
.replies .comment__avatar{width:var(--avatar-reply);height:var(--avatar-reply)}
```

## 수정·삭제는 ⋯ 뒤에 두고, 지워진 부모 댓글은 자리를 남긴다

수정·삭제 메뉴의 위치는 국내 플랫폼과 해외 디자인 시스템이 다르다. 국내 플랫폼은 **오른쪽 위 ⋮/⋯ 오버플로 버튼**을 쓴다. 네이버 카페는 20×20px ⋮ 버튼을 27px 폭 오른쪽 열의 하트 좋아요 버튼 위에 둔다. 브런치의 "설정" ⋯ 버튼은 테두리가 있는 작은 드롭다운(13px 항목, 위아래 9px 패딩)을 열고, 남의 댓글에서는 "신고"만 보여 준다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css); [브런치 댓글 CSS](https://t1.kakaocdn.net/brunch/home_front/prod/20260928145833/_astro/comment.CouC7HU1.css); [브런치](https://brunch.co.kr/@brunch/1)). 디자인 시스템은 본문 아래에 텍스트 액션을 한 줄로 늘어놓는다. Atlassian은 "Reply · Edit · Like"를 가운뎃점으로 잇고 ([Atlassian Comment](https://atlassian.design/components/comment/examples)), Ant Design은 본문 아래 12px 여백을 두고 12px 회색 액션을 10px 간격으로 놓는다 ([antd comment less](https://raw.githubusercontent.com/ant-design/ant-design/4.x-stable/components/comment/style/index.less)). Primer는 액션을 오른쪽에 정렬하고, 컨테이너 폭이 480px보다 좁아지면 아래 줄로 넘긴다 ([Primer Timeline CSS](https://raw.githubusercontent.com/primer/react/main/packages/react/src/Timeline/Timeline.module.css)). 모바일 앱은 제스처도 쓴다. Slack은 모바일에서 길게 눌러 보조 액션을 열고 ([Slack 도움말](https://slack.com/help/articles/115000769927-Use-threads-to-organize-discussions-)), 디스코드는 UI 개편 뒤 오른쪽에서 왼쪽으로 밀면 답장이 시작되게 바꿨다가 "예전엔 멤버 목록을 여는 동작이었다"는 혼란을 낳았다 ([Discord 커뮤니티](https://support.discord.com/hc/vi/community/posts/19989495753751-New-Discord-Mobile-UI-Feedback)). 일기 앱에서는 두 방식을 섞는다. 가장 자주 쓰고 발견돼야 하는 "답글"은 모든 댓글 아래에 보이는 텍스트로 두고, 드물게 쓰는 수정·삭제는 **내 댓글에만** ⋯ 메뉴로 숨긴다. 길게 누르기는 지름길로만 쓰고 유일한 경로로 만들지 않는다.

터치 영역은 글자 크기와 따로 확보해야 한다. 최소 터치 크기는 Apple HIG가 44×44pt, Material Design이 48×48dp이고, WCAG 2.2는 AA에서 24×24 CSS px, AAA에서 44×44를 요구한다. HIG와 Material 수치는 원문 페이지가 아니라 이를 인용한 2차 출처로 확인한 값이다 ([specification.website](https://specification.website/spec/accessibility/touch-target-size/); [Front-End Checklist](https://frontendchecklist.io/rules/accessibility/touch-targets)). KRDS도 링크 컴포넌트에 터치 기준 44×44px를 요구한다. 다만 이 수치는 검색 결과 발췌로만 확인했다 ([KRDS 링크](https://www.krds.go.kr/html/site/component/component_05_01.html)). 이 기준에 비추면 네이버 카페의 20×20 ⋮ 아이콘과 14px/19px "답글쓰기" 텍스트는 보이는 크기로는 모자라고, Primer의 액션 최소 높이 32px도 모바일 기준 아래다. 글리프는 작게 두더라도 패딩으로 히트 영역을 44px까지 넓히고, 음수 마진으로 글자 위치는 본문 열에 맞춘다. 이웃한 액션의 히트 영역이 겹치지 않게 사이를 띄운다.

삭제 확인은 실행 취소를 먼저 고려한다. 네이버 카페는 단순한 "삭제하시겠습니까?" 확인창을 띄우고, BEST 댓글에는 "BEST 댓글 목록에서 제외됩니다"라는 경고를 먼저 보여 준다 ([네이버 카페 모바일 JS](https://ca-fe.pstatic.net/web-mobile/js/app.2dd3b3f070bc.js)). NN/g의 원칙은 더 엄격하다. 확인창은 **되돌릴 수 없는 동작에만** 쓰고 가능하면 실행 취소를 제공하라고 한다. 일상적인 동작에 확인창을 남발하면 사용자가 읽지 않고 누르게 된다. 확인창은 요청 내용을 다시 말해 주고, 버튼에는 "예/아니오" 대신 "파일 삭제/파일 유지"처럼 동작을 담은 이름을 붙이며, 기본 선택값을 두지 않는다 ([NN/g Confirmation Dialogs](https://www.nngroup.com/articles/confirmation-dialog/)). 가벼운 일기 댓글에는 즉시 삭제하고 "댓글을 삭제했어요 · 실행 취소" 스낵바를 잠시 띄우는 방식이 가장 잘 맞는다. 실행 취소를 구현할 수 없다면 "댓글을 삭제할까요?" 시트에 "취소"와 빨간 "삭제" 버튼을 두고 기본 선택은 두지 않는다.

지워진 부모 댓글은 자리를 남긴다. 네이버 카페는 삭제된 댓글을 `blind_post` 안의 "삭제된 댓글입니다." 회색 16px 문구로 바꾸되, 행 높이와 구분선과 **답글 수 표시를 그대로 유지**해서 답글이 계속 닿게 한다 ([네이버 카페 모바일 JS](https://ca-fe.pstatic.net/web-mobile/js/app.2dd3b3f070bc.js); [네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css)). 당근은 이름을 "알 수 없는 사용자"로, 본문을 "삭제되었거나 존재하지 않는 댓글이에요."로 바꾸고, 아바타는 기본 아이콘으로 대체하되 시간과 그 아래 답글은 남긴다. 운영 정책으로 가린 댓글에는 "동네생활 운영정책에 따라 숨김 처리 되었어요."처럼 '~요'체의 친근한 문구를 쓴다 ([당근 동네생활](https://www.daangn.com/kr/community/%EC%83%A4%EC%9B%8C%EA%B8%B0%EA%B1%B0%EC%B9%98%EB%8C%80-%ED%9C%B4%EC%A7%80%EA%B1%B8%EC%9D%B4-%EC%88%98%EA%B1%B4%EA%B1%B8%EC%9D%B4-h9v1co6o28y6/)). 해외도 사용자 보고 기준으로 비슷하다. Reddit은 사용자가 지운 댓글을 "[deleted]", 운영진이 지운 댓글을 "[removed]"로 구분해 남기고 답글을 보존한다. Lemmy는 부모를 지우면 답글까지 숨기고, 디스코드는 지운 메시지가 흔적 없이 사라진다 ([lemm.ee](https://lemm.ee/post/4488635/2351116); [Tildes](https://tildes.net/~tech/16on/reddit_is_silently_restoring_deleted_edited_comments); [Discord 커뮤니티](https://support.discord.com/hc/it/community/posts/360042614551-Delete-Time-Stamps)). 일기 앱에서는 답글이 달린 댓글을 지우면 아바타를 흐리게 한 "삭제된 댓글이에요" 행을 남기고, 답글이 없으면 행 자체를 없앤다. 후자는 관찰한 사례가 아니라 추론이다.

'수정됨' 표시는 국내외 관행이 갈리는 지점이다. 해외 플랫폼은 대부분 표시한다. 인스타그램은 2026년 4월 모든 사용자에게 댓글 수정을 열면서 **15분 수정 창**을 두었다. 그 안에서는 몇 번이든 고칠 수 있고, 수정된 댓글에는 "Edited" 라벨이 붙지만 이전 내용은 볼 수 없다 ([Vaizle](https://insights.vaizle.com/news/instagram-adds-comment-editing-with-a-15-minute-window); [Inro](https://www.inro.social/blog/comment-editing-on-instagram)). 페이스북은 게시물에서는 수정 라벨을 없앴지만 댓글에는 타임스탬프 옆에 남겨 두었고, 라벨을 누르면 수정 이력이 열린다 ([VentureBeat](https://venturebeat.com/ai/facebook-makes-it-harder-to-notice-when-posts-are-edited); [Louise Myers](https://louisem.com/1620/how-to-edit-facebook-comment)). 디스코드는 본문 옆에 작은 "(edited)"를 붙이는데, 지저분하다며 연필 아이콘으로 바꿔 달라는 요청이 있다 ([Discord 커뮤니티](https://support.discord.com/hc/vi/community/posts/360042841131-Changing-the-position-of-the-edited-label-A-new-icon-for-it-QoL-change)). Atlassian은 헤더에 `edited` 슬롯을 따로 둔다. 반면 네이버 카페 모바일 JS 번들(약 6.4MB)에서 "수정됨" 문자열은 **0회** 나온다. 같은 번들에서 "삭제된 댓글"은 2회 나온다 ([네이버 카페 모바일 JS](https://ca-fe.pstatic.net/web-mobile/js/app.2dd3b3f070bc.js)). 수정 화면도 다르다. 네이버 카페는 최소 높이 256px textarea가 있는 별도 전체 화면으로 넘어가고, 브런치는 댓글을 `.comment.editing` 상태로 바꿔 그 자리에서 편집한다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css); [브런치 댓글 CSS](https://t1.kakaocdn.net/brunch/home_front/prod/20260928145833/_astro/comment.CouC7HU1.css)). 세 줄 남짓한 일기 댓글에는 브런치식 제자리 편집이 가볍다. 메타 줄 시간 뒤에 같은 회색으로 "· 수정됨"을 붙이면 소음 없이 투명성을 지킬 수 있다.

## 입력창은 하단 알약형으로 두고, 비었을 때만 보내기를 흐린다

국내 플랫폼의 입력창은 접혀 있다가 쓸 때 펼쳐진다. 네이버 카페 모바일은 화면 양옆 16px 안쪽에 **`border-radius: 99px`의 알약형 입력창**을 연회색 #f5f6f7로 채워 둔다. textarea는 15px, 접힌 높이는 19px이다. 탭하면 모서리 6px의 카드로 펼쳐지면서 18px 아바타와 닉네임, 오른쪽의 `N/max` 바이트 카운터, 스티커·파일 아이콘과 등록 버튼이 있는 49px 높이 푸터가 나타난다 ([네이버 카페 모바일 CSS](https://ca-fe.pstatic.net/web-mobile/css/app.da9ebbc5d389.css)). 안내 문구는 댓글이 0개면 "첫 댓글을 남겨보세요", 있으면 "댓글을 남겨보세요"로 상황에 따라 바뀌고, 댓글을 막은 글에는 "댓글쓰기가 허용되지 않은 글입니다."를 띄운다 ([네이버 카페 모바일 JS](https://ca-fe.pstatic.net/web-mobile/js/app.2dd3b3f070bc.js)). 브런치는 1px #ddd 테두리 상자에 최소 높이 78px textarea를 두고, 52×32px 알약형 등록 버튼을 쓴다. 이 버튼은 회색 테두리 상태로 있다가 **글자를 입력하면 검정 배경에 흰 글씨로 바뀐다** ([브런치 댓글 CSS](https://t1.kakaocdn.net/brunch/home_front/prod/20260928145833/_astro/comment.CouC7HU1.css)). 당근은 댓글이 없을 때 "아직 댓글이 없어요 / 가장 먼저 댓글을 남겨보세요."와 "댓글 쓰기" 버튼을 보여 준다 ([당근 빈 상태](https://www.daangn.com/kr/community/%EC%83%88%EB%B2%BD%EB%A7%8C-%EB%90%98%EB%A9%B4-%EC%9A%B0%EB%8A%94-%EA%B3%A0%EC%96%91%EC%9D%B4-%EA%B3%A0%EB%AF%BC-97dfybar5kkz/)).

해외 채팅 SDK들은 보내기 버튼 규칙을 문서로 정해 두었다. MUI X Chat은 입력이 비었거나 응답이 스트리밍 중이면 보내기를 비활성화하고, **IME 조합 중에는 Enter로 제출하지 않는다** ([MUI X Chat Composer](https://mui.com/x/react-chat/basics/composer/)). 비활성 버튼에 대한 비판도 함께 봐야 한다. 비활성 버튼은 흔히 대비가 부족하고, 포커스를 받지 못하며, 왜 못 누르는지 알려 주지 않는다. 그럼에도 Slack과 Microsoft Teams는 사용자가 입력하기 전까지 보내기를 비활성으로 둔다 ([UX Planet](https://uxplanet.org/disabled-buttons-ux-usability-issues-and-how-to-avoid-them-8f2246186e80)). 빈 입력창의 흐린 보내기 버튼은 이유가 눈에 보이므로 비판의 예외에 가깝다. 다만 흐린 상태에서도 아이콘을 알아볼 수 있는 대비는 유지한다.

일기 앱에는 다음 구성을 권한다. 입력창은 댓글 영역 하단에 `position: sticky; bottom: 0`으로 고정하고, `padding-bottom`에 `env(safe-area-inset-bottom)`를 더한다. 다른 댓글의 "답글"을 누르면 같은 입력창에 포커스를 주고, 위에 닫을 수 있는 "○○님에게 답글 ×" 칩을 띄운다. Slack처럼 입력창을 하나로 유지하는 방식이다. 입력창은 한 줄에서 시작해 4–5줄(약 120px)까지 늘어나다가 그 뒤로는 내부 스크롤한다. 지원하는 브라우저에서는 `field-sizing: content`로 JS 없이 처리할 수 있다. 입력 글자는 KRDS 본문 최소치인 16px로 맞춘다. 보내기 버튼 상태는 `value.trim()===''`일 때, 그리고 전송 중일 때 막는다. 모바일에서는 Enter를 줄바꿈으로, 보내기 버튼을 제출로 두고, 한글 IME에서 Enter를 처리할 때는 반드시 `event.isComposing`을 먼저 확인한다. 카운터는 바이트가 아니라 글자 수로 세고, 한도에 가까워질 때만 보인다. 네이버 카페의 바이트 카운터는 영어 위주 텍스트에는 어색하다. 영어 학습 맥락이라면 "Write a comment in English…" 같은 영어 안내 문구도 고려할 만하다. 키보드가 올라올 때 고정 입력창이 실제로 어떻게 움직이는지(`visualViewport` 처리 등)는 실기기와 로그인 없이 관찰하지 못했으므로 기기 테스트로 확인해야 한다.

## 중복 제출은 즉시 전환, 늦은 스피너, 좁은 잠금으로 막는다

중복 제출은 실제로 일어나는 문제다. GOV.UK Notify에서는 사용자가 "보내기"를 두 번 눌러 초대장이 두 번 발송됐다. GOV.UK는 원인으로 습관적으로 더블클릭하는 사용자, 피드백 없는 느린 연결, 손떨림 같은 운동 장애를 꼽는다. 대응책인 `preventDoubleClick`은 **첫 클릭 후 1초 안의 반복 클릭을 무시하는** 단순 디바운스다. 기본으로는 꺼져 있고, 실서비스 조사에서 중복 전송이 확인될 때만 켜라고 한다 ([GOV.UK Button](https://design-system.service.gov.uk/components/button/); [govuk-frontend 소스](https://raw.githubusercontent.com/alphagov/govuk-frontend/main/packages/govuk-frontend/src/govuk/components/button/button.mjs)). 모바일 네트워크에서는 요청 하나가 1초를 쉽게 넘기므로, 시간 기반 디바운스보다 **요청이 끝날 때까지 유지하는 진행 중 플래그**가 더 확실하다.

버튼 자체의 피드백은 디자인 시스템마다 형태만 다를 뿐 원칙은 같다. Atlassian은 로딩 스피너를 라벨 자리에 띄우고 상호작용을 막는다 ([Atlassian Button](https://atlassian.design/components/button/examples)). Shopify Polaris는 비동기 작업에 `disabled` 대신 `loading`을 쓰라고 한다. 진행 중이라는 사실을 알려 주기 때문이다. 라벨은 "Saving product..."처럼 구체적으로 쓰고, **`loading`만 믿지 말고 핸들러에서도 반복 실행을 막으라고** 덧붙인다 ([Polaris Button](https://shopify.dev/docs/api/app-home/polaris-web-components/actions/button)). Apple HIG는 대기 중 라벨을 "Checkout"에서 "Checking out…"으로 바꾸는 예를 든다. 이 문구는 apple.com이 아니라 제3자 미러로만 확인했다 ([HIG Buttons 미러](https://glama.ai/mcp/servers/@tmaasen/apple-dev-mcp/blob/b82f0efe2115dc4539c83a2374a714a84aeb350a/content/universal/buttons.md)). React 문서의 예시도 클릭 즉시 "Submitting..."을 보여 준다 ([react.dev useOptimistic](https://react.dev/reference/react/useOptimistic)). 한국어로는 "등록"을 "등록 중…"으로, "저장"을 "저장 중…"으로 바꾸면 된다. 다만 한국어 진행형 라벨은 원래보다 길어지므로, Primer가 경고한 "거슬리는 레이아웃 이동"을 막으려면 폭을 미리 고정해야 한다 ([Primer Loading](https://primer.style/product/ui-patterns/loading/)). 바꾸기 직전에 `minWidth`를 현재 폭으로 잠그는 것만으로는 늘어나는 라벨을 막지 못한다. 라벨과 스피너를 같은 grid 셀에 겹쳐 두고 `visibility`만 바꾸거나, 처음부터 긴 라벨 폭을 확보해 둔다.

스피너를 띄우는 시점에는 근거가 있다. NN/g는 0.1초 안의 반응은 즉각적으로 느껴지고, 1초를 넘으면 컴퓨터가 일하고 있음을 보여 줘야 하며, 10초를 넘으면 주의를 잃는다고 정리한다 ([NN/g Response Times](https://www.nngroup.com/articles/response-times-3-important-limits/)). 같은 NN/g는 **1초 미만 작업에 반복 애니메이션을 쓰면 오히려 산만하다**고 하면서도, 버튼 상태 변화 같은 즉각적인 시각 피드백은 필요하다고 한다. "다시 누르지 마세요" 경고 대신 첫 클릭이 접수됐음을 보여 주라는 것이다 ([NN/g Progress Indicators](https://www.nngroup.com/articles/progress-indicators/)). Primer는 1초 미만이면 로딩 상태를 아예 보이지 말라고 한다. 깜빡이는 표시가 오히려 제품을 느리게 느끼게 만들기 때문이다. 1–3초에는 진행률 없는 표시를 쓴다 ([Primer Loading](https://primer.style/product/ui-patterns/loading/)). spin-delay 라이브러리는 문제를 양쪽에서 짚는다. 너무 빠른 요청에 스피너를 그리면 해가 되고, 단순 지연만 두면 임계값을 살짝 넘긴 요청에서 "10ms짜리 스피너"가 깜빡인다. 그래서 기본값을 **500ms 지연, 최소 표시 200ms**로 둔다 ([spin-delay README](https://cdn.jsdelivr.net/npm/spin-delay@2.0.1/README.md)). 이를 종합하면 탭한 순간 라벨만 바꾸고, 스피너는 약 400ms 뒤에 붙이고, 일단 보이면 최소 300–400ms는 유지한다. 최소 표시 시간을 공식으로 정한 1차 출처는 없으므로 이 값은 라이브러리 기본값에 기댄 절충이다.

잠금 범위는 같은 대상에 충돌하거나 중복될 수 있는 컨트롤로 좁힌다. Primer는 제출 뒤 폼 컨트롤 전체를 비활성화해 저장 중임을 알려도 된다고 한다 ([Primer Loading](https://primer.style/product/ui-patterns/loading/)). React 문서의 항목별 패턴은 삭제 중인 항목만 흐리게 하고 취소선을 그은 뒤 그 항목의 버튼만 막는다. 나머지 항목은 계속 쓸 수 있다 ([react.dev useOptimistic](https://react.dev/reference/react/useOptimistic)). 다른 댓글까지 잠그라고 권하는 권위 있는 출처는 찾지 못했다. 그러니 원칙은 같은 대상에 충돌하는 요청을 만들 수 있는 컨트롤만 잠그는 것이다. 버튼만 잠그면 전송 중인 텍스트를 사용자가 고칠 수 있어 혼란스러운 결과가 나온다. 페이지 전체를 잠그면 불안정한 모바일 망에서 몇 초씩 아무것도 못 하게 된다. 구현은 전역 플래그 하나 대신 `'comment:123:delete'` 같은 키를 쓰는 대상별 진행 중 맵으로 하고, 같은 키를 아래의 멱등 키와 연결한다.

갱신 방식은 동작마다 고른다. React 문서는 낙관적 상태를 "작업이 끝나기 전에 결과를 즉시 보여 주는 것"으로 정의한다. 대기 항목에는 "(Adding...)" 같은 표시를 달고, 성공하면 표시만 떼어 낸다. 실패하면 UI가 원래 값으로 돌아가므로 오류 메시지는 개발자가 직접 띄워야 한다 ([react.dev useOptimistic](https://react.dev/reference/react/useOptimistic)). Atlassian Comment의 `isSaving` 모드는 저장 중인 댓글을 바로 보여 주되 액션을 숨기고 "Saving..."을 띄운다. 느린 연결에서도 빠르고 반응적인 경험을 주기 위한 장치다 ([Atlassian Comment](https://atlassian.design/components/comment/examples)). 실패하면 무엇이 잘못됐는지 설명하고 재시도를 제공해야 한다 ([Primer Loading](https://primer.style/product/ui-patterns/loading/)). 재시도를 안전하게 만드는 것은 서버의 멱등 키다 ([Stripe](https://docs.stripe.com/api/idempotent_requests)). 이를 일기 댓글에 적용하면 다음 표가 된다. 서버가 길이 제한이나 금칙어로 내용을 거절할 수 있다면 등록도 비관적 방식이 기본이 되어야 한다. 낙관적으로 잠깐 보여 줬다가 거절되면 사용자를 속이는 셈이기 때문이다.

| 동작 | 갱신 방식 | 잠그는 범위 | 진행 중 표시 | 실패 시 |
|---|---|---|---|---|
| 댓글 등록 | 낙관적 | 보내기 버튼 + textarea `readOnly`(`disabled` 아님) | 목록 끝에 흐린 댓글 + "전송 중…" | 그 자리에 "전송 실패 · 다시 시도", 입력한 글 보존, **같은 멱등 키로 재전송** |
| 댓글 수정 | 낙관적 | 해당 댓글의 저장·취소·수정·삭제 | "저장 중…" | 원문 복원, 편집 모드로 돌아가 사용자가 고친 글 유지, 오류 표시 |
| 댓글 삭제 | 비관적 또는 실행 취소 | 해당 댓글 액션 전체 + 흐림 처리 | "삭제 중…" 또는 "삭제했어요 · 실행 취소" | 원상태로 되돌리고 오류 표시. 재시도 응답이 404면 성공으로 처리 |

삭제를 낙관적으로 처리했다가 실패해서 되돌리면 지운 댓글이 "다시 나타나는" 어색한 장면이 생긴다. 그래서 삭제는 서버 확인 뒤에 지우거나, 서버 호출을 미루는 실행 취소 방식이 낫다. 어떤 경로든 지켜야 할 규칙은 하나다. **사용자가 입력한 글은 절대 사라지면 안 된다.**

## 버튼은 포커스를 유지하고, 최종 방어는 서버 멱등 키가 맡는다

로딩 버튼을 `disabled`로 막을지에 대해서는 의견이 갈리지만 무게는 한쪽으로 기울었다. GitLab 디자인 시스템 이슈는 로딩 중인 버튼에 네이티브 `disabled`를 걸면 스크린리더가 접근하지 못하고 탭 순서에서 빠져 **포커스를 잃는다**고 보고한다. 해결책은 `aria-disabled="true"`를 걸고, 클릭 이벤트는 스크립트로 무시하고, 비활성 모양은 CSS로 내는 `accessibleLoading` 옵션이었다 ([GitLab #2981](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/issues/2981)). ARIA는 동작을 바꾸지 않으므로 클릭 차단은 반드시 JS로 해야 한다 ([CSS-Tricks](https://css-tricks.com/?p=339960)). W3C APG 메일링 리스트의 정리도 같다. 포커스를 유지해야 하면 `aria-disabled`, 아니면 HTML `disabled`를 쓴다 ([public-aria-practices](https://lists.w3.org/Archives/Public/public-aria-practices/2023Jul/0006.html)). Salt 디자인 시스템은 사용자나 시스템이 다시 활성화할 수 있는 요소라면 포커스를 받을 수 있게 두라고 한다. 곧 다시 눌러야 할 로딩 버튼이 정확히 그런 경우다 ([Salt Button](https://saltdesignsystem.com/salt/components/button/accessibility)). Adrian Roselli는 한발 더 나아가 폼 컨트롤 비활성화 자체가 대체로 나쁘다고 본다. 비활성 스타일은 WCAG 대비 기준에서도 면제돼 신호가 약하다는 것이다 ([Roselli](https://adrianroselli.com/2024/02/dont-disable-form-controls.html)). GOV.UK도 비활성 버튼은 대비가 낮고 혼란을 주니 가능하면 피하라고 한다 ([GOV.UK Button](https://design-system.service.gov.uk/components/button/)). 반대편에는 로딩 상태를 실제로 비활성화하는 Atlassian과 Polaris가 있다. Polaris는 비활성 버튼이 탭 순서에서 빠진다는 점을 스스로 인정한다 ([Polaris Button](https://shopify.dev/docs/api/app-home/polaris-web-components/actions/button)). Primer는 동작을 시작한 버튼에 `aria-disabled`를 걸지 말라고 하는데, 이 문장은 요약 도구를 거쳐 얻은 것이라 원문과 다를 수 있다. 그래도 Primer와 GitLab은 버튼이 계속 닿아야 한다는 점에서는 같은 편이다. 결론은 이렇다. 버튼은 포커스를 받을 수 있게 두고, `aria-disabled="true"`, 비활성 모양, JS 가드를 함께 건다. 가드는 `click`, 폼 `submit`, Enter 키 등 **모든 실행 경로**에서 돌아야 한다. `pointer-events: none`만으로는 키보드와 보조기기의 실행을 막지 못한다.

상태 알림은 라이브 영역이 맡는다. MDN은 `aria-busy`를 요소가 "수정되는 중"임을 뜻하는 전역 상태로 정의한다. 보조기기는 수정이 끝날 때까지 기다렸다가 `aria-live` 값에 따라 알리며, 주 사용처는 라이브 영역·위젯·피드다. 버튼에 쓰는 법은 다루지 않는다 ([MDN aria-busy](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-busy)). Primer는 상태 메시지를 **항상 렌더된 `role="status"` 요소**나 `aria-live` 영역으로 알리고, 영역이 갱신되는 동안만 `aria-busy="true"`를 걸라고 한다. 실패하면 오류 메시지 안의 첫 포커스 가능 요소로 포커스를 옮긴다 ([Primer Loading](https://primer.style/product/ui-patterns/loading/)). 일기 앱에 옮기면 이렇게 된다. 처음 HTML에 시각적으로 숨긴 `<div role="status">`를 하나 두고, "댓글 등록 중…", "댓글이 등록되었습니다", "댓글 등록에 실패했습니다. 다시 시도 버튼을 누르세요." 순으로 `textContent`를 바꾼다. `aria-busy`는 낙관적 추가·삭제 동안 댓글 목록 `<ul>`이나 해당 `<li>`에 건다. 스피너 SVG는 `aria-hidden="true"`로 두어 두 번 읽히지 않게 한다. 포커스는 다음처럼 옮긴다. 등록에 성공하면 비워진 입력창에 둬서 이어 쓰게 한다. 삭제하면 포커스를 갖던 요소가 사라지므로 이웃 댓글의 액션이나 목록 제목으로 옮긴다. 수정을 저장하면 그 댓글의 수정 버튼으로, 실패하면 재시도 버튼으로 보낸다. 움직임 줄이기 설정에 대해서는 의견이 갈린다. GitLab은 스피너가 상태 이해에 필수라며 `prefers-reduced-motion`에서도 돌린다 ([GitLab Spinner](https://design.gitlab.com/components/spinner)). Primer는 로딩 애니메이션을 은은하게 유지하라고 한다. 표시를 숨기지 말고 회전 속도만 늦추는 정도가 안전하다. VoiceOver와 TalkBack이 포커스된 버튼의 라벨 변화를 실제로 읽어 주는지는 검증된 자료가 없어 실기기 테스트가 필요하다.

클라이언트 잠금은 UX일 뿐 정합성을 보장하지 못한다. GOV.UK는 자기들의 중복 클릭 방지가 JS가 켜진 사용자에게만 작동하니 서버에서도 대비하라고 명시한다 ([GOV.UK Button](https://design-system.service.gov.uk/components/button/)). Roselli 역시 스크립트는 언제든 실패할 수 있으니 중복 제출은 백엔드에서 처리해야 한다고 한다 ([Roselli](https://adrianroselli.com/2024/02/dont-disable-form-controls.html)). 표준적인 해법은 클라이언트가 만든 멱등 키다. Stripe는 V4 UUID 같은 키(최대 255자)를 받아 **첫 요청의 상태 코드와 본문을 저장하고, 재시도에는 500 오류까지 포함해 같은 응답을 돌려준다.** 키는 24시간 이후 정리할 수 있고, 같은 키에 다른 파라미터가 오면 오류를 낸다 ([Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests)). IETF의 `Idempotency-Key` 헤더 초안 07판은 POST/PATCH에 이 헤더를 붙이도록 하고 상태 코드를 정해 둔다. 필수 키가 없으면 400, 같은 키를 다른 내용에 재사용하면 422, 원 요청이 아직 처리 중이면 409다. 다만 이 초안은 RFC가 되지 못하고 만료된 문서다 ([IETF draft-07](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html)). 구현은 단순하게 할 수 있다. 사용자가 처음 보내기를 누를 때 `crypto.randomUUID()`로 키를 만들어 초안과 함께 성공할 때까지 보관한다. "다시 시도"에도 같은 키를 쓰고, 내용이 바뀔 때만 새 키를 만든다. 서버는 `(user_id, key)`에 유일 제약을 걸어 중복 삽입이 원자적으로 실패하게 한다. 이렇게 하면 클라이언트 잠금, 재시도 버튼, 낙관적 항목이 모두 키 하나로 묶인다. 키를 도입하기 어렵다면 같은 사용자·같은 일기·같은 본문을 N초 안에 거부하는 방법이 있다. 다만 이 방법은 의도한 동일 댓글까지 막고 응답을 재생하지 못하는 약한 대안이다. 백엔드가 Firebase나 Supabase라면 그 플랫폼에 맞는 중복 제거 방식은 이번 조사에서 확인하지 않았다.

```js
const inFlight = new Map();                       // 'comment:new', 'comment:123:delete' …
async function runAction(btn, key, busyLabel, fn) {
  if (inFlight.has(key)) return;                  // 반복 탭 무시 (click·submit·Enter 공통 진입점)
  inFlight.set(key, true);
  btn.setAttribute('aria-disabled', 'true');      // 포커스 유지, 네이티브 disabled 미사용
  const label = btn.querySelector('.label'), original = label.textContent;
  label.textContent = busyLabel;                  // 즉시(<100ms) '등록 중…'
  status.textContent = busyLabel;                 // 처음부터 존재하는 role="status"
  let shownAt = 0;
  const t = setTimeout(() => { btn.classList.add('is-spinning'); shownAt = Date.now(); }, 400);
  try { return await fn(); }                      // fn 안에서 Idempotency-Key 헤더 전송
  finally {
    clearTimeout(t);
    const wait = shownAt ? Math.max(0, 400 - (Date.now() - shownAt)) : 0;
    setTimeout(() => {
      btn.classList.remove('is-spinning'); label.textContent = original;
      btn.removeAttribute('aria-disabled'); inFlight.delete(key);
    }, wait);
  }
}
```

## 결론

이번 조사에서 가장 의외였던 점은 핵심 결정이 픽셀 수치에 있지 않다는 것이다. 아바타·간격·글자 크기는 이미 몇 px 범위로 수렴했으니 어느 쪽을 골라도 틀리지 않는다. 실제로 갈리는 결정은 세 가지다. 댓글을 선으로 나눌지 여백으로 나눌지, 두 참여자를 아바타로 구분할지 배경색으로 구분할지, 수정 사실을 드러낼지다. 특히 '수정됨'은 국내 관행(표시 안 함)과 해외 관행(표시함)이 정면으로 갈리는 지점이다. 영어 학습 일기에서는 친구가 표현을 고쳐 다시 올리는 일 자체가 학습 흔적이므로, 인스타그램식 15분 수정 창과 은은한 "· 수정됨" 표시가 국내 관행보다 이 앱의 목적에 더 맞을 수 있다.

중복 제출 방지도 버튼 하나의 문제가 아니라 상태와 식별자의 문제로 보는 편이 정확하다. 초안이 만들어질 때 생긴 멱등 키 하나가 클라이언트의 진행 중 맵, 낙관적 항목의 "전송 중…" 표시, 실패 시 재시도, 서버의 중복 제거를 모두 관통한다. 이 축을 먼저 세우면 버튼을 `disabled`로 막을지 같은 논쟁은 부차적인 문제가 된다. 남은 불확실성은 측정으로만 풀린다. 실기기 VoiceOver·TalkBack에서 라벨 변화가 읽히는지, 키보드가 올라올 때 고정 입력창이 어떻게 움직이는지, Apple HIG·Material 3 원문 수치가 2차 출처와 같은지는 구현 전에 한 번씩 확인할 가치가 있다.
